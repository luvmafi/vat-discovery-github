# Research report — Phase 0

I started with an unrelated local workspace and created an isolated VAT-discovery POC directory. I expected no usable VAT dataset or experiment results to be present; inspection confirmed no pre-existing VAT project, input population, or result set.

I therefore tested no external source and made no live HTTP, search, HMRC, or crawling request. The observed result is only that Phase 0 design artifacts are in place. This changes no viability conclusion: source coverage, precision, entity accuracy, and economics remain unknown.

Next experiment: acquire a dated, permitted Companies House population snapshot, construct and retain the deterministic 500-company sample manifest, then run a small company-website accessibility and signal experiment. The source matrix must be updated with observed counts before a source is scaled.

# Research report — Phase 1

I downloaded the real Companies House "Basic Company Data" snapshot dated 2026-08-01 (single file, 5,695,465 rows) and ran the ingestion module against it for the first time. I expected most rows to convert cleanly since the module was built against the documented column set. It did not: `rows_kept` was 0 out of 5,695,465. The snapshot's actual header pads several column names with a leading space (` CompanyNumber`, ` RegAddress.AddressLine2`, etc.) — undocumented on the download page and not reproducible from the field-list PDF alone, only visible by inspecting the real file's first line directly. This is an implementation-specific failure, not a fundamental one: the data was there, the key just didn't match. Fixed by stripping header names before building each row dict, added a regression test, and reran.

Second run: 5,190,464 of 5,695,465 rows had `CompanyStatus == Active`; the remainder split across Liquidation (108,797), Active - Proposal to Strike off (388,951), and ten smaller administration/receivership statuses. Generated the deterministic 500-company sample (seed 20260815, reference date 2026-08-01) against the 5,190,464 active rows; all 50 populated industry/age strata received at least one company, so no stratum was silently dropped by rounding.

This changes no viability conclusion yet — no VAT evidence has been sought. It does confirm the population backbone and sample are real, not fabricated, and it surfaced one lesson worth keeping: never trust a bulk-data field spec at face value; verify against the first line of the actual file before writing a parser that assumes it.

Next experiment: run one small, documented company-website accessibility and VAT-signal test against a handful of sampled companies, per the experiment-first rule, before building any scaled crawler.

# Research report — Phase 2 pilot (company website / search)

I expected at least a few of a small stratum-spread subset of the sample to have a findable, entity-confirmed website with visible VAT text, since UK companies commonly publish VAT numbers in footers/terms pages. I picked 8 companies at evenly spaced indices across the 500-row sample (not the easiest-looking names, to avoid the bias the brief explicitly warns against) and, for each, ran one search-engine query for the company name plus "official website", then attempted to fetch and verify any candidate.

No credentialed search API exists in this project yet (`.env.example` only has HMRC placeholders), so this pilot could not exercise the `SearchProvider` adapter interface as a live, automated, reproducible pipeline. Instead I used the operating agent's own web-search and page-fetch tools directly as a documented, manual stand-in — labelled `AGENT_MEDIATED_SEARCH_AND_FETCH` in the experiment record, never conflated with a production adapter run.

The result was negative on every axis I set out to measure: 0 of 8 produced a confirmed, entity-matched website; 0 of 8 produced any VAT evidence. The failure modes were varied and instructive, not one dominant cause:

- Five companies (CADWELL CORPORATION L.P., TURQUOISE REAL ESTATE LIMITED, GXFC LTD, CEUTICA LIMITED, MEAT N SHAKE LTD) simply had no discoverable web presence via a single query — several are small SPVs/LPs/holding entities, one is a generic enough name that an unrelated US chain restaurant dominated the results.
- One (KNOTAGAIN INTERNATIONAL LTD) matched a same-named company in a different country entirely — confirmed via Companies House address that it was the wrong entity before rejecting it, not after guessing.
- One (NORTH LONDON GROUP LTD) had the single most promising-looking result — a plausible-sounding domain that loads successfully — but the page itself carries no company name, address, or registration text of any kind, so entity match could not be established even though the domain resolves.
- One (CHURCHGATE WOKING LTD) had a search snippet whose stated address matched the company's real Companies House registration exactly, which looked like strong indirect evidence — but the domain itself no longer resolves at all (DNS failure), so nothing could be confirmed.

This changes my view: I did not expect zero confirmed matches out of eight. It is a small sample and a single, naive query strategy, so I am not treating this as a source-level NO-GO for company websites in general — but it is real evidence that a single-query, first-result search approach is measurably too weak, and that the recently-formed/SPV-heavy tail of the Companies House population (which this sample deliberately did not exclude) may be structurally hard to find via generic web search regardless of query sophistication. All eight observations, including the negative ones, are recorded with full provenance in `data/vat_discovery.sqlite` (`websites`, `source_experiments`) and `experiments/source_website.py`.

Next experiment: before concluding on the source, rerun a larger pilot (n≈25-30) using the brief's suggested multi-query strategy per company (section 30) and Companies House SIC/name text to disambiguate multi-result cases — the current pilot cannot distinguish "no signal in this source" from "this specific query strategy is too weak."

# Research report — Phase 4 (public PDFs)

Before writing a PDF crawler, I built the extraction module first (`src/vat_discovery/extraction/pdf.py`, text-layer only via `pypdf`, deliberately no OCR by default) and unit-tested it against synthetic PDFs generated with `fpdf2`, so the code itself was ready and verified independent of whether any real PDF could be found.

I then piloted discovery using the exact same 8 companies as the Phase 2 website pilot, so the two source results would be directly comparable, with one query per company: `"<company name>" filetype:pdf VAT`. I expected at least a couple of hits, since invoices, terms sheets, or filed documents sometimes surface this way even for small companies. Instead: zero of eight produced a company-specific PDF at all, not merely a PDF lacking VAT text. Search results were dominated by unrelated same-named companies in other countries or registries, generic VAT-compliance guidance documents with no connection to any target company, and for two companies, results about a completely different topic (Woking churches for CHURCHGATE WOKING LTD; the US chain Steak 'n Shake for MEAT N SHAKE LTD).

This is a clean negative result, and it changes my read of the project's viability question further downward for these specific acquisition methods, though not definitively: a single `filetype:pdf` query is at least as weak a signal as the single-query website search from Phase 2, and I cannot yet separate "small UK companies rarely have indexed PDFs" from "this exact query pattern fails to surface them." The one PDF source I have not yet tried is Companies House's own filed-accounts documents, which exist for essentially every company registered here — but I am flagging in advance, not discovering after the fact, that accounts filings and VAT registration are different regulatory regimes, so I do not expect a VAT number to appear in a standard filed-accounts PDF even when one is found. That expectation itself should be tested, not assumed, before ruling the source in or out.

Next experiment: either scale the multi-query Phase 2 retest (website discovery) since it is the more promising of the two sources tested so far, or run one small pilot against Companies House filed-accounts PDFs specifically to test the accounts-vs-VAT-regime hypothesis above, before committing further effort to open-web PDF search.

# Research report — Phase 2 retest (round 2)

I retested the same 8 companies with a disambiguated query (town plus a sector keyword pulled from each company's real Companies House record) to find out whether the round-1 NO-GO reflected the source or just a weak query. I expected disambiguation to at least reduce the noise from unrelated same-named companies, even if it didn't produce a confirmed VAT.

It did not change the outcome: still zero new confirmed websites and zero new VAT evidence across all 8. What it did surface was more useful than a null result alone — one additional concrete wrong-entity near-miss (a company called "MEAT AND SHAKES (PRESTON) LIMITED," company number 13198421 in Manchester, which is not our sampled "MEAT N SHAKE LTD," company number 17295865 in Preston) and one unrelated VAT number appearing incidentally on a property-listing page with zero connection to the company being searched for. Both were rejected on company-number/address grounds rather than merged, which is the entire point of not trusting name similarity alone.

This changes my view in a specific way: I now trust the round-1 NO-GO more, not less, because a second, better-informed attempt on the same companies produced the same result plus new evidence of exactly the failure mode the brief warns about most (section 15/23: verified-but-wrong-entity). Two real false-positive traps across two rounds, on only 8 companies, is a meaningful signal on its own, independent of the discovery-rate question.

Next step: rather than run a third search-methodology variant on the same 8 companies, I built the entity resolution scorer next (Phase 8) using these two real traps as regression tests, since they are more informative than any fixture I could invent, and because the scorer needs to exist before any future pilot's candidates can be meaningfully evaluated at all.

# Research report — Phase 8 (entity resolution scoring)

I built the multi-signal entity resolution scorer against the weights and tier thresholds already defined in `config/scoring.yaml` back in Phase 0 (name 0.35, address 0.20, postcode 0.15, domain 0.10, company number 0.15, context 0.05; TIER_1 requires verified status, total score ≥0.85, and at least one of postcode/company-number match at full strength). I did not invent new thresholds — the earlier Phase-0 design already specified them; this phase is the first to actually exercise them.

I tested it primarily against the two real wrong-entity near-misses from the Phase-2 pilots rather than synthetic cases, since they are stronger evidence than anything I could construct: KNOTAGAIN INTERNATIONAL LTD against the unrelated South African retailer, and MEAT N SHAKE LTD against the differently-numbered MEAT AND SHAKES (PRESTON) LIMITED. Both correctly fail to reach TIER_1 (the second one specifically because its address and company number contradict the target company even though "MEAT" and "SHAKE(S)" overlap in the name). I also found and fixed a real bug while writing the first clean positive-case test: my initial address/postcode/company-number matching compared against punctuation-uncleaned context text, so a trailing comma after a street name silently broke an otherwise-correct match and pushed a should-be-TIER_1 case down to TIER_2. This is exactly the kind of small implementation bug the project's own philosophy (verify against real data before trusting a design) is meant to catch before it reaches anything resembling production.

The scorer has not yet been run against a real, live-discovered candidate, because neither pilot so far produced one. It is ready for the moment one does. This changes no coverage or precision conclusion, but it means the pipeline's most important non-negotiable ("a checksum-valid, HMRC-verified VAT is still not proof of ownership") is now enforced by working, tested code rather than only a design document.

Next experiment: with website and PDF search both showing weak signal at n=8, and entity resolution now ready to consume whatever a source produces, the highest-value next step is either (a) the larger n=25-30 multi-query website pilot to get a more statistically defensible read on that source, or (b) building the HMRC verifier adapter's remaining scaffolding so that if either pilot does produce a candidate, the full pipeline (extract → normalize → verify → resolve → tier) can run end-to-end at least once, even in dry-run/sandbox form.

# Research report — Phase 10 (manual validation, n=100, complete)

At the user's direction, I reviewed all 100 companies in the deterministic manual-validation subset myself, using the same tools as the Phase 2 pilots, rather than the independent human review the brief originally specifies. I flagged this distinction before starting and tagged every recorded row accordingly, because conflating the two would quietly undermine the entire point of having a manual-validation phase in the first place -- it exists to catch what the automated approach can't see, and an agent-run review inherits the same blind spots.

It caught them anyway, twice more. Working through the 100 companies in five batches of twenty, I found three more claimed VAT numbers I could not trust on the search summary alone: FIREBIRD MUSIC LIMITED's claimed number led to a domain that, when fetched directly, turned out to belong to an unrelated company in Phoenix, Arizona; BRISTOL ENERGY & TECHNOLOGY SERVICES (SUPPLY) LIMITED's claimed number was not present in the PDF that was supposedly its source, when I fetched and read that PDF myself; and MOIRA FINE JEWELLERY LIMITED's claim could not be checked at all because the site returned a 403 on every page I tried, combined with an address that didn't match the Companies House record. All three were rejected. Combined with AQUAWASH LIMITED from Phase 2, that is four rejected claims out of roughly ten VAT numbers this project has investigated in total -- a real, load-bearing finding: search-result summaries are not evidence, and I only avoided recording four fabricated-or-unconfirmed VAT numbers as real discoveries because I insisted on fetching and reading the actual source page every time, not because the summaries looked implausible on their face. They didn't.

Six claims did hold up under direct verification: HILLS FAMILY LTD and JTHN LIMITED (both already found during the earlier Phase 2 round 3 pilot), and four new ones from this batch -- GO2 PROPERTY SERVICES LIMITED, G A PLANT AND TOOL HIRE LTD, TTG PORTSMOUTH LIMITED, and BULLET BUILDING PRODUCTS LIMITED. Two of the six (JTHN, GO2) have a registered address that doesn't exactly match the address shown on the company's own website, which I did not treat as disqualifying -- the company-number match was exact in both cases, and the brief's own scoring design treats that as sufficient corroboration on its own. I logged the discrepancy rather than either hiding it or rejecting a company-number-confirmed candidate over it.

Processing G A PLANT AND TOOL HIRE LTD, JTHN LIMITED, and GO2 PROPERTY SERVICES LIMITED through the actual pipeline surfaced something I did not expect: all three failed `validate_uk_vat_syntax` under both implemented checksum rules, despite the strongest possible corroborating evidence (exact company-number match on a first-party page). I did not shrug this off as "checksum is only a filter, so it doesn't matter" -- that principle is about not treating a passing checksum as proof, not about ignoring a real, repeated failure that contradicts strong independent evidence. I derived the correct formula for the "9755" legacy variant by hand against these three real numbers, found the implemented formula had a sign error (`standard + 42` where it should be `42 - standard`), fixed it, added regression tests using the three real numbers rather than only synthetic ones, and corrected the already-inserted database rows. This is very likely the single most consequential bug fix in the project so far: an unfixed version of this module would have silently misclassified most real UK VAT numbers using this specific, common check scheme as syntactically invalid, in any system built on top of it.

Every one of the six confirmed candidates -- including G A PLANT AND TOOL HIRE LTD, which scores 0.96 out of 1.0 on the entity-resolution model with no address discrepancy at all -- is still capped at TIER_3, "candidate only, not a discovery," because `verification_status` is honestly `UNAVAILABLE`. No HMRC credentials exist. This is not a disappointing result; it is the Phase 0 design (written before any real data existed) holding up under six independent real tests. The project's central remaining question has stopped being "does this source have any signal" -- it clearly does, at roughly 5% and rising in confidence with sample size -- and has become entirely "can we get authoritative verification." Every other piece of this pipeline (extraction, normalization, entity resolution, economics) is now built, tested, and has processed real data at least once. Verifier access is the one gap nothing in this session could close.

# Research report — HMRC Sandbox integration

The user obtained HMRC Developer Hub Sandbox credentials -- I confirmed with them directly that these were Sandbox, not production, since Sandbox credentials are issued instantly on registering an application while production requires the ~2-week approval process discussed earlier, and the timing between those two conversations made Sandbox the near-certain answer. This mattered enough to ask outright rather than assume: treating a Sandbox result as a real verification would have been exactly the kind of fabrication this entire project has been built to avoid.

With that confirmed, I built `verification/hmrc_api.py` against HMRC's actual published OpenAPI spec for the v2 "Check a UK VAT Number" API -- OAuth 2.0 client_credentials against `/oauth/token` with scope `read:vat`, then `GET /organisations/vat/check-vat-number/lookup/{vrn}` -- rather than guessing at the shape of the API from memory. I also pulled a real test VRN from HMRC's own public GitHub test-data file instead of inventing one, since a plausible-looking-but-made-up VRN would not have been a fair test of the integration.

The first live call worked: a real OAuth token exchange, a real HTTP round-trip to `test-api.service.hmrc.gov.uk`, and a parsed `VERIFIED` result for HMRC's own mock company ("Credite Sberger Donal Inc.", obviously synthetic test data, not a real business). This is the first real network call to an external verification authority anywhere in this project. `experiments/hmrc_sandbox_test.py` refuses to run unless `.env` is explicitly set to `HMRC_ENVIRONMENT=sandbox`, specifically so this script can never accidentally be pointed at production with an unapproved credential, and it was never run against any of this project's 6 real candidates -- sandbox data cannot verify anything real regardless of which VAT number is queried.

This changes the project's remaining gap from "verification is entirely unbuilt" to "verification is built, tested against a live HMRC server, and waiting only on a production credential." That is a meaningfully smaller gap than it was at the start of this session, even though the actual missing input -- production access -- has not changed.

# Research report — Phase 2 round 3 (extended pilot, n=28 new)

I extended the website-discovery pilot from n=8 to 28 new companies (36 distinct companies total across all three rounds), still using the round-2 disambiguated-query style, to get a more statistically defensible read on whether the source has any signal at all. I expected the true rate to be somewhere above zero given 36 is still a small sample, but I did not expect to find real candidates this specific pilot round — the first sixteen company-rounds (8×2) had produced none.

Two companies produced genuine, first-party VAT evidence I could directly confirm by fetching their own websites: HILLS FAMILY LTD ("VAT No. 420840821" in the site footer, next to "Company Registration No. 14228579" — an exact match to the sampled company) and JTHN LIMITED ("VAT Registration Number 183 3256 07" next to "Registered in England No. 08250395" — also an exact company-number match). I ran both through the actual pipeline code rather than reasoning about them by hand: `extraction.html.extract_vat_candidates`, then `normalization.vat.validate_uk_vat_syntax`, then `entity_resolution.scoring.score_match`, with results written to `data/vat_discovery.sqlite` via `experiments/source_website_round3.py`.

Both landed at TIER_3 ("candidate only, not a discovery"), which is correct, working behavior, not a disappointing result: I have no HMRC credentials, so `verification_status` is honestly `UNAVAILABLE` for both, and the scorer is designed to cap any unverified candidate at TIER_3 no matter how strong the surrounding evidence is. This is the first time that specific design decision — made back in Phase 0, before any real data existed — has been exercised against a real candidate, and it held.

Two things surprised me enough to investigate rather than gloss over. First, JTHN's VAT number fails our own checksum validator (`validate_uk_vat_syntax` returns `syntax_valid=False` under both the standard and 97-55-variant rules) despite the exact company-number match giving strong independent reason to believe it's real. I did not "fix" this by loosening the checksum rule to make the number pass — that would be tuning the validator to a single data point. I recorded it as an open gap: UK VAT numbers have more than the two checksum schemes this module currently implements, and this candidate is evidence the coverage is incomplete, not evidence the number is fake. Second, and more concerning: a third claimed VAT number, for AQUAWASH LIMITED, appeared in a search-tool's summary text but was not present anywhere on the actual page when I fetched it directly to confirm. I did not merge it. This is a different, arguably more dangerous failure mode than anything found in rounds 1-2 (wrong entity, stale domain) — it's the discovery *tooling itself* asserting evidence that doesn't exist. I only avoided recording a fabricated VAT number because I independently re-fetched and checked every claim before writing it down, which is exactly the "verify, don't trust" discipline the brief asks for throughout, now demonstrated as necessary rather than theoretical.

This changes my read of the source materially: company websites are not a zero-signal source, as rounds 1-2 alone would have suggested — the true rate across 36 companies (2/36, ~5.6%) is low but real and non-zero. What is now actually blocking a "reportable discovery" is not the source, and not entity resolution (which correctly handled the real candidates and the real near-misses alike) — it is the complete absence of an authoritative verification path. That is now the single most concrete, evidence-backed argument in this project for prioritizing HMRC verifier access next, rather than a purely hypothetical one.

Next experiment: pursue the HMRC verifier adapter (credentials/onboarding permitting), since that gap — not discovery — is now the binding constraint on producing an actual TIER_1 result; in parallel, extending the query strategy to a larger n (100+) is now justified by a measured non-zero base rate rather than a guess.
